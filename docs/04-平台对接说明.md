# 平台对接说明

面向平台建设方的落地指引。

## 1. 对接边界

QACD 是**后处理评分组件**，不参与回答生成。平台的既有 LVLM 推理链路不需要改动，
只需在回答产生之后追加一次评分调用。

```
平台既有链路:  图像 + 问题 ──► 平台 LVLM ──► 回答 ──► 业务

接入后:        图像 + 问题 ──► 平台 LVLM ──► 回答 ──┬──► 业务
                                                    │
                                                    └──► QACD 评分 ──► 风险分
                                                                        │
                                                            ┌───────────┼───────────┐
                                                        风险低        风险中        风险高
                                                        直接放行    人工复核      预警/拒答
```

## 2. 平台需要提供的三样东西

| 项 | 说明 | 是否可先用占位 |
|---|---|---|
| **带标签开发集** | ≥1,200 条回答，标注"该回答是否正确"；字段 `question/answer/image/failed/group` | 否，必须有 |
| **LVLM 推理环境** | 被评估模型（默认 LLaVA-1.5-13B）的推理服务；需支持同 prompt 多次采样（MVR 用） | 否，必须有 |
| **图像 OCR 能力** | RapidOCR 即可，CPU 运行 | 可先用离线 JSONL 缓存替代 |

> ⚠️ **重要**：`qacd fit` / `qacd serve` 的默认证据提供方是 `MockProvider`（确定性、无模型），
> 用于**打通接口与自测**。生产环境必须注入 `LLaVAProvider` + `RapidOCRProvider`
> （见 `qacd/providers.py`），否则得到的是链路演示值，不是 QACD 分数。
> 服务启动时必须校验 `GET /health` 的 `scorer_fitted` 为 `true`。

## 3. 三个技术点的接入顺序（建议）

| 阶段 | 内容 | 前置依赖 | 验收方式 |
|---|---|---|---|
| 一 | 技术点 3：机械 OCR 通道 | 仅 OCR 引擎 | 单测 128 项通过 + `/v1/qacd/mechanical` 返回 19 项特征 |
| 二 | 技术点 1：核心打分器 | LVLM + 开发集 | 冻结测试上的 AUROC 复现（见下） |
| 三 | 技术点 2：MVR 通道 | 阶段二的 LVLM 采样能力 | K=3 相对 K=0 的 ΔAUROC 区间为正 |
| 四 | 技术点 4：保形弃权 | 平台自己的校准批次 | `/v1/qacd/select` 返回的覆盖率与 realized FDP |

## 4. 验收标准

### 阶段二（核心打分器）

平台应在**自己的**留出集上复现方向一致的结果，判据建议：

- 回答级 AUROC ≥ 0.80（参考值：冻结 TextVQA 测试 0.8495，图像级 0.8608）
- 风险分与"回答错误"单调正相关，按风险分五等分后各组错误率单调递增
- `warnings` 为空或仅含可解释项

**不要**用内部指标去对撞论文数值——平台数据分布不同，数值不可比。

### 阶段三（MVR）

- K=3 相对 K=0 的 ΔAUROC 配对 bootstrap 95% CI 下界 > 0
- 每回答模型调用次数不超过预算（K=3 时为 10.61 次）

### 阶段四（保形弃权）

在平台自己的校准批次上运行：传入已知正确样本的风险分与待判定样本的风险分，
读取返回的 `coverage` 与 `realized_fdp` 决定工作点。
可用覆盖率随校准集规模变化，建议先用历史数据试跑一版看曲线形状。

## 5. 必须拦截的两种情况

| 情况 | 判别方式 | 平台动作 |
|---|---|---|
| 打分器未拟合 | `GET /health` → `scorer_fitted: false`，或响应 `warnings` 含 `scorer is not fitted` | 拒绝将 `risk_score` 写入业务库 |
| 特征维度不匹配 | 响应 `feature_dim` 与平台记录不一致 | 拒绝，触发告警（意味着打分器版本变更） |

## 6. 阈值选取

`threshold` 默认 0.5（自然概率切点），**仅用于 `is_high_risk` 这个布尔量**。
研究侧评估的是排序（AUROC/AUPRC）与概率质量（Brier/NLL），**没有**调优过阈值。

平台应按自己的错误成本选取运行阈值，方法：

1. 在平台留出集上取若干阈值；
2. 对每个阈值算"误报率（把正确回答标为高风险）"与"漏报率（放过错误回答）"；
3. 按业务成本比选择工作点；
4. 通过请求体的 `threshold` 字段传入，**不要**改服务端冻结配置。

## 7. 监控建议

| 指标 | 用途 |
|---|---|
| 高风险率（`is_high_risk` 占比） | 漂移检测；显著偏离历史值时告警 |
| `risk_score` 分布（分位数） | 分布漂移 |
| `num_claims` 直方图 | 分解行为变化（应集中在 1，多主张占比异常说明输入形态变了） |
| `warnings` 计数按类型 | 质量退化预警 |
| `model_calls` 累计 | 成本核算（算力成本代理） |
| `latency_ms` 分位数 | 性能（首次上线即应开始采集，作为容量基线） |

## 8. 常见问题

**Q：能不能只用一个分数，不要 `claims` 明细？**
可以，请求体传 `"return_claims": false`。但建议至少在上线初期保留明细，便于排查误报。

**Q：平台用的是别的 LVLM（不是 LLaVA-1.5-13B），能用吗？**
可以用，但**必须重新拟合校准器**并在平台自己的留出集上重新评估。冻结系数是针对
LLaVA-1.5-13B 开发的，换模型后不复用。

**Q：能不能用于中文场景？**
分解提示、主张类型词表和 OCR 匹配逻辑目前都是英文导向。中文场景需要重新设计分词与
相似度计算，需单独立项评估。

**Q：0.85 这个量级还能往上提吗？**
这是回答级**精确匹配错误**代理上的排序能力。提升路径包括：
增加 MVR 的 K（收益递减）、扩大开发集（学习曲线显示 1,200 条后收益很小）、
或引入人工标注的主张级标签（属于新研究，不在当前范围）。
